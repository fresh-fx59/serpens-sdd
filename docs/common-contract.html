The Common Contract

One shape, one owner, one file. Every repository that touches it links that file — and a lint fails the commit if anyone pastes the shape instead. This is how serpens-sdd keeps a cross-repo contract from forking into five slightly different truths.

01 / the problemWhy a contract needs an owner

A product spread over five repositories has facts that live between them: an event payload, an endpoint shape, a table the consumer reads. Nobody owns "between".

Write that shape into each repository's spec and you get five copies. They agree on the day they are written. Then the producer adds a field, one consumer's copy is updated, and the other four become confidently wrong documentation — the worst kind, because agents and people both read it as fact.

serpens-sdd calls that failure split brain, and treats it as the thing the whole design exists to prevent. The rule it enforces:

one spec-truth

A cross-repo contract fact lives in exactly one place — the system store. A spoke repository links the store contract. It never restates the shape.

"Never restates" is not a convention in a README. It is a check that exits non-zero.

02 / topologyHub, spokes, and the shape of the disk

Two kinds of Git repository, and they are never nested. The hub is the system store: an independent repository holding contracts, ADRs, conventions, and the project's repositories as submodules. The spokes are the code repositories themselves.

the nesting trap

OpenSpec resolves its root by walking up from the current directory looking for an openspec/ folder — and the walk does not stop at a .git boundary (verified on OpenSpec 1.7.0). A submodule that was never openspec init-ed therefore resolves to the store's root, and every spec the agent writes silently lands in the hub. check-openspec-root.sh exists only to refuse that.

03 / the storeHow the OpenSpec store actually works

"Store" is OpenSpec's own mechanism for reading specs that live in another repository. Three moving parts, and each one has to be true or the link is dead.

  1. A

    Register the path under a stable id

    The hub's absolute path is registered once per machine with the pinned CLI. This writes the machine-local registry.

    <openspec> store register /work/acme/system-store --id acme-store --yes
<openspec> store list      # must print that id + exact path

    Ids are a contract, not a label. Cross-repo links resolve by id, so two people installing the same project must produce the same string. The kit fixes the convention: <project-id>-store for the store, the repository name for each repo, both lower-case kebab-case, both recorded in port-facts.md.

  2. B

    Declare the reference in every spoke

    In each onboarded repository's openspec/config.yaml:

    references:
  - acme-store

# better, where the CLI accepts the map form: a machine that has not registered
# the store then gets a pasteable clone+register line instead of a bare failure
references:
  - id: acme-store
    remote: git@git.acme.internal:acme/system-store.git

    This block is what makes a spoke able to link instead of restate. Two things break without it, and both are silent:

    • Neither fetch route resolves — the lines spns-spec writes into every cross-repo delta.
    • check-contract-split-brain.mjs exits 0 without checking anything, because it scopes itself to repos that declare references:. A pasted contract shape then goes unnoticed.
  3. C

    Read the contract through the store, at read time — and there are TWO windows

    A spoke delta spec carries fetch lines, not a payload. It carries two, because the routes never overlap. The contract merges last, so for the entire cross-repo window the contract exists only inside its change folder; archiving it deletes that folder at the same moment the spec route starts working.

    contract: payments-events-v2 in store acme-store (change add-payments-events-v2)

while the contract change is open:
  <openspec> show add-payments-events-v2 --type change --store acme-store --json --deltas-only

after the contract change is archived:
  <openspec> show payments-events-v2 --type spec --store acme-store

which window am I in:
  <openspec> list --specs --store acme-store   # spec id absent → still open

if the CLI refuses (broken contract proposal, unregistered store), read the file:
  <openspec> instructions specs --change add-payments-events-v2 --store acme-store --json   # prints changeDir
  cat <changeDir>/specs/payments-events-v2/spec.md
    measured, openspec 1.10.0 · 2026-08-26

    Before the archive, the spec route is dead: ✖ Error: Spec 'payments-events-v2' not found at /…/acme-store/openspec/specs/payments-events-v2/spec.md, exit 1. After the archive, the change route is dead: Change "add-payments-events-v2" not found — and the dated archive id does not resolve either.

    --json is mandatory on the change route. Without it the CLI prints proposal.md only, omits the delta silently, and still exits 0 — a worse trap than the dead link, because nothing fails.

    Never use <openspec> change show or <openspec> spec show here: the noun-first forms have no --store flag at all and resolve against the spoke. <openspec> context prints only the spec recipe, so it cannot be trusted during the open window either.

    Recording the contract change id beside the spec id is not optional: while the change is open, the spec id resolves nothing.

    <openspec> is one token the install resolves once — npx @fission-ai/openspec@<pinned> or an internal wrapper on PATH. The kit deliberately calls the CLI, never a generated slash command: slash commands differ between versions and profiles (OpenSpec 1.10's core profile ships propose, explore, apply, update, sync, archive and has no new, continue or verify at all), while the CLI calls are stable and machine-readable.

    OpenSpec never inlines store content into the spoke. The spoke's own delta describes only what this repository does with the contract — which fields it emits, which it consumes, what it does on a missing one.

What the contract file itself looks like

The hub's contract is a template with one job: be the only place the shape appears. Note the embed pointer — the shape is pulled from the producer's real source through the submodule, never transcribed by hand.

# Contract: payments-events-v2

- Producer: service-a · Consumers: service-b, service-c · Status: active
- Owning change history: ACME-4412

## Shape
<!-- THE one place this contract's facts live. Spoke specs LINK here, never restate. -->
<!-- embed: submodules/service-a/src/main/proto/payment.proto#L12-L48 -->
```
<embedded schema source>
```

## Compatibility rules
<what a consumer may rely on; what the producer may change without notice>

The trust order behind that embed is absolute and worth memorising: live code > repo living spec > repo index > central catalog > wiki. Lower levels may only route you upward; only code and living specs may be quoted as fact. For a field name or an event shape you read the source and embed it — you never quote a spec's prose for a shape when the source is one hop away.

04 / enforcementThe split-brain lint, in detail

Where OpenSpec's references: guarantees the tool never inlines store content, nothing stops a human or an agent from pasting the payload into a spoke's delta by hand. check-contract-split-brain.mjs catches exactly that. Zero dependencies, so it runs on a restricted network.

Fails the lint

A spoke delta that pastes the payload so "the reader has it handy". The heading matches a store requirement; the fence matches a store shape. ✗ exit 1

Passes the lint

A spoke delta with its own requirement about this repository's behaviour, plus the two labelled openspec show … --store fetch lines. ✓ exit 0

Where the check runs

The lint is not a separate ritual. It is one of three calls inside verify-docs.sh, the single disposer entry point — and that one script is wired to four triggers so no actor can bypass it.

# tools/verify-docs.sh — one code path
node tools/gen-index.mjs --check
node tools/serpens-lint.mjs
node tools/check-contract-split-brain.mjs   # no-op in repos with no references:
TriggerActorEffect of a red result
agent post-write self-checkthe coding agent, after touching openspec/ or docs/cannot report the work done; regenerates the content
lefthook pre-committhe humancommit rejected
on demandanyone—
CI stage docs-disposerthe pipelinebuild fails; the backstop
operating rule

Prompts advise; the disposer and CI enforce. Never fix a red check by weakening it. Caps reject, they never trim — the agent regenerates the content, and humans never hand-repair a generated file. If the same error survives three fix attempts, the agent stops and asks a human rather than looping.

05 / workflowContract first — the order that makes it hold

The lint stops a duplicated shape. Ticket and merge order stop something else: a consumer shipping against a contract that was never agreed. In serpens-sdd a cross-repo story is one parent plus one child per repository, and the parent is the contract.

What spns-spec does with all this

The analyst-facing command decides the shape before creating anything, and refuses to fan out for the wrong reason:

  • Interview once, at story level — even for five repositories. The requirements are shared; asking per repo asks the same question five times and invites five different answers.
  • Count the repos. One repo → single-repo path. More than one → is there a genuine shared contract, a shape or protocol crossing the boundary? If not, it says "not a cross-repo change; this is N independent stories" and stops.
  • Contract first. In the store: prepare base, branch feature/<parent-ticket>, create the contract change from store-contract.md, verify, push, PR, post the link on the parent story.
  • Then each repo, one at a time. Its own delta links the contract by store id, spec id and contract change id, and includes both fetch lines — the change-scoped one for the open window, the spec-scoped one for after the merge. Verified facts go to research.md as pointers — path#Lx-Ly plus a one-line finding, never pasted payloads, which rot and bloat context.
  • Where you stand decides where the files land. Every path is resolved by git rev-parse --show-toplevel, and a registered submodule is its own Git root — so cd into the submodule first, then resolve REPO_ROOT, and assert it is not STORE_ROOT. If they are equal you are still in the store and every artifact would land in the wrong repository.
  • Normative versus discovered. Facts this change defines — a new endpoint, a new field, a new topic, the error contract — belong in the delta spec's requirement text and scenarios, where they are reviewed and archived. Facts the change only discovers about the system as it already is go to research.md as pointers.
  • Two green gates per artifact: verify-docs.sh, then <openspec> validate <change-id> --type change --strict --json reporting "valid": true.
  • Gates recorded on every child: approval order, implementation order, merge order, and the rule that a contract change stops all repos.

If the split-brain lint fires at step (c) of that per-repo loop, the instruction to the agent is one sentence: you restated a contract fact — delete it and link instead.

06 / setupWiring it properly

The contract machinery only works if four things are true on disk. These are the lines from the kit's setup runbook that specifically make the common contract resolvable — the full install has nine stages.

  1. i

    Pin the real OpenSpec package

    The package is @fission-ai/openspec. The bare name openspec on the public registry is an unrelated empty 0.0.0 placeholder and will silently install nothing usable.

    npx @fission-ai/openspec@<pinned-version> --version

    Record the pinned version in port-facts.md. On a restricted network, resolve it through the approved internal mirror and note the resolved registry.

  2. ii

    Put the store beside the kit, never inside it

    export SERPENS_SDD_ROOT="$(git rev-parse --show-toplevel)"
export SERPENS_WORKSPACE_ROOT="$(cd "$SERPENS_SDD_ROOT/.." && pwd -P)"
export SERPENS_SYSTEM_STORE_ROOT="${SERPENS_SYSTEM_STORE_ROOT:-$SERPENS_WORKSPACE_ROOT/system-store}"
test "$SERPENS_SYSTEM_STORE_ROOT" != "$SERPENS_SDD_ROOT"

    Then let Git decide which of three cases you are in — never guess, and never ask a person something Git can answer:

    git ls-remote --heads "<store-remote>" "<store-base-branch>"

    A printed ref means the store already exists: clone it. Running the template path here would git init a second, unrelated history against a remote that already holds the project's store — the one mistake in that stage that costs a rewrite rather than a retry. Nothing printed, and this is the first install anywhere: copy system-store-template/, then git init. Already on this machine: touch neither, and gate its branch and worktree with repository-state.sh prepare-base.

  3. iii

    Register the store, and prove the root before anything else

    Initialize OpenSpec in the store with the pinned package, run the root check, then register the absolute path under the stable <store-id> and prove openspec store list returns that id and that exact path. Do not run another OpenSpec command until its root is verified.

  4. iv

    Onboard each submodule so it can link

    Per repository reported by .gitmodules: prepare-base, openspec init with the pinned package, check-openspec-root.sh proving the root is that submodule, copy the spoke tools into tools/, install lefthook, add openspec/repo.txt with a stable repository id, generate the index, run verify-docs.sh — and declare the store:

    # <repo>/openspec/config.yaml
references:
  - <store-id>

    Then append the write-boundary rule to the project instruction file the port actually reads, in every onboarded repository and in the store:

    ## HARD RULE — disposer self-check
After creating or editing ANY file under openspec/ or docs/, run:
    bash "$(git rev-parse --show-toplevel)/tools/verify-docs.sh"
Fix every ✗ and re-run until green BEFORE reporting work done.
CIRCUIT BREAKER: same error surviving 3 attempts → STOP and ask a human.

    If one submodule cannot be onboarded, finish the others and leave that one un-onboarded rather than half-onboarded — a partial repository is the one state the daily flow cannot detect. Name it in the handover with the failing gate and its output.

  5. v

    Prove the guards with bad input, then with a real command

    Before trusting any of it: a bad OpenSpec root must fail; a duplicated shared contract shape must fail the split-brain check; a bad branch and mismatched ticket commit must fail naming checks; a deliberate bad temporary commit must be rejected by the installed hook. Never weaken a guard to make this green.

    Files on disk are not a working install. Run spns-spec against a throwaway ticket in one onboarded repository, confirm it reaches the interview and writes openspec/changes/<id>/proposal.md, then delete the branch and the change folder.

08 / in one paragraphThe mechanism, compressed

The system store owns every cross-repo shape in one spec.md, and that shape is embedded from the producer's real source rather than retyped. The store is registered once per machine under a stable id; each spoke declares that id in openspec/config.yaml and links the contract with two labelled fetch lines — show <change-id> --type change --store <id> --json --deltas-only while the contract change is open, show <spec-id> --type spec --store <id> once it is archived, because those two routes never overlap. OpenSpec never inlines the store's content, so the link cannot fork. A hand-paste still can — so a zero-dependency lint fingerprints the store's requirement headings and multi-line code fences and fails any spoke spec that repeats one, naming the owner. That lint runs inside the one disposer script the agent, the pre-commit hook, and CI all call. On top of that, ticket order makes the contract a parent ticket approved before its children, and merge order ships producer, then consumers, then the contract itself. One shape, one owner, one file — and three actors who cannot commit around it.

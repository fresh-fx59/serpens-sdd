description: Создать delta spec истории; при необходимости разнести её по репозиториям
serpens-version: 2026-09-23.1

Ты готовишь спеку для истории {{args}}. Следуй spns-drill-down и spns-verification.
`<change-id>` — имя папки изменения OpenSpec; `<openspec>` — вызов CLI OpenSpec, подставленный при
установке.

1. ПРОЧИТАЙ И ПРОВЕДИ ОДНО ИНТЕРВЬЮ. Получи историю, wiki и вложения через
   настроенную интеграцию. Если её нет, используй предоставленный экспорт и пометь
   недостающие доказательства. В каждом выбранном репозитории установи
   `REPO_ROOT="$(git rev-parse --show-toplevel)"` и выполни
   `<serpens-sdd> state inspect`. Прочитай только нужные
   живые спеки и проверь каждый факт контракта по коду. Задавай аналитику по одному
   вопросу, пока требования и Given/When/Then не станут однозначными. Каждый сценарий должен называть,
   что тестировщик ОТПРАВЛЯЕТ и что НАБЛЮДАЕТ снаружи работающей системы: запрос, событие, строку,
   код статуса. Требование, проверяемое только изнутри, либо переформулируй в наблюдаемое сейчас,
   пока это одно предложение, либо отдай в `spns-autotest` и скажи об этом вслух. Это самый дешёвый
   момент во всём потоке, чтобы это найти. Для нескольких
   репозиториев интервью всё равно одно.

2. ОПРЕДЕЛИ ФОРМУ И ПОДТВЕРДИ ДО ИЗМЕНЕНИЙ. Один репозиторий — шаг 3. Несколько
   репозиториев без общей формы или протокола — это независимые истории, остановись.
   При общем контракте — шаг 4. До создания ticket, ветки, коммита или PR покажи
   аналитику репозитории, producer, существующие и новые tickets, число PR и дождись
   подтверждения. Не делай fan-out молча.

3. ОДИН РЕПОЗИТОРИЙ. Сначала определись, ГДЕ ты, и только потом что-то создавай.
   a. ТИКЕТ. Имя ветки строится из реального ключа трекера. Если его нет ни в `{{args}}`,
      ни в истории, ветку назвать нечем: спроси пользователя ОДИН раз — (1) создать тикет сейчас
      через интеграцию с трекером, (2) он даёт ключ, (3) напиши черновик спеки БЕЗ ветки и БЕЗ папки
      изменения и прямо скажи, что передать работу нельзя, пока тикета нет. НИКОГДА не придумывай
      ключ, не бери заголовок истории и не называй ветку по заглушке вроде `NO-TICKET`.
   b. ИМЯ ВЕТКИ НЕ ТЫ ПРИДУМЫВАЕШЬ. Спроси его — форма принадлежит команде, живёт в
      `serpens/branching.md`, и pre-push hook требует ровно то, что печатает эта команда:
      ```bash
      BRANCH=$(<serpens-sdd> git-naming --print-contract <TICKET> | awk -F'\t' '$1=="branch-example"{print $2}')
      ```
      Дальше используй `$BRANCH` дословно. Никогда не собирай имя сам, не предполагай никакой
      префикс, и не добавляй описание в конец: придуманное имя не проходит
      pre-push guard, и push отклоняется. Ненулевой код возврата здесь означает, что файл
      конвенций команды сломан: сообщи и остановись, а не подставляй догадку.
   c. ГДЕ ТЫ. Ветка может уже существовать, и ты можешь уже быть на ней. Сначала посмотри:
      ```bash
      git -C "$REPO_ROOT" rev-parse --abbrev-ref HEAD
      git -C "$REPO_ROOT" show-ref --verify --quiet "refs/heads/$BRANCH" && echo local
      git -C "$REPO_ROOT" ls-remote --heads origin "$BRANCH"
      ```
      - УЖЕ НА `$BRANCH` → НЕ запускай `prepare-base`: он переключит на базовую ветку и
        уведёт тебя с твоей работы. Выполни `assert-change <TICKET> --allow-dirty` и продолжай здесь.
        Если `openspec/changes/<change-id>/` уже есть — ПРОДОЛЖИ её, не создавай заново и не вызывай
        `<openspec> new change` второй раз.
      - ЕСТЬ ЛОКАЛЬНО, но ты не на ней → `git checkout "$BRANCH"`, затем
        `assert-change <TICKET> --allow-dirty`, дальше как выше.
      - ЕСТЬ ТОЛЬКО НА ORIGIN → `git fetch origin`, затем
        `git checkout -b "$BRANCH" --track "origin/$BRANCH"`, затем `assert-change`.
      - НЕТ НИГДЕ → выполни `<serpens-sdd> state prepare-base`; при ошибке
        остановись. Создай `$BRANCH` от настроенной базы, опубликуй её
        `git push -u origin "$BRANCH"`, затем выполни
        `<serpens-sdd> state assert-change <TICKET>`.
      Задай пользователю ОДИН вопрос, показав найденное состояние, если оно противоречиво: локальная
      и удалённая ветки разошлись, локальная отслеживает не `origin/$BRANCH`, или папка
      изменения принадлежит другому тикету. Не угадывай.
   c. Выполни `<openspec> new change <change-id>` — пропусти, если папка изменения уже есть.
      Затем выполни `<serpens-sdd> state mark-change <change-id> --ticket <TICKET>` — идемпотентно,
      возобновлённое изменение без метки её получит. Дальше спрашивай CLI по ОДНОМУ артефакту; `<openspec> status --change <change-id> --json` —
      источник истины о том, какие артефакты нужны этой схеме и в каком они состоянии; никогда не
      считай список идентификаторов зафиксированным. Эта команда владеет `proposal` и `specs` —
      теми двумя, которых не касается `spns-plan`:
      ```bash
      <openspec> instructions proposal --change <change-id> --json
      ```
      Дальше проверь состояние `specs`, прежде чем его трогать. `skipped` значит, что
      `.openspec.yaml` этого изменения задаёт `skip_specs: true` — законное «без изменений на
      уровне спеки»; считай его выполненным и НЕ создавай delta spec (собственный валидатор
      CLI отвергает delta spec у изменения с `skip_specs: true`). Любое другое состояние — выполни:
      ```bash
      <openspec> instructions specs --change <change-id> --json
      ```
      Каждый вызов возвращает указания и точный путь вывода для этого артефакта; напиши его и
      переходи к следующему. Остановись, когда есть `proposal.md`, а `specs` в состоянии `done`
      или `skipped`: `design` и `tasks` — это `spns-plan`, он запрашивает их так же. В research.md
      сохраняй только указатели path#Lx-Ly и краткий вывод.
   Раздели факты тестировщика по владельцу. То, что это изменение ЗАДАЁТ — новая поверхность,
   новое поле, новая точка назначения, контракт ошибок — нормативно и живёт в delta-спеке, в
   тексте требования и его сценариях, где оно проходит ревью и попадает в архив. То, что
   изменение только ОБНАРУЖИВАЕТ в системе как она есть, идёт в research.md под заголовком
   `## OBSERVABLE CONTRACT` указателями.
   ЧТО ИМЕННО В ЭТОМ БЛОКЕ — это факт ЭТОГО репозитория, а не этой команды. Прочитай
   `serpens/testing-stack.md` и следуй его разделу `Ручной доступ для тестирования`: записывай по
   одному указателю на каждый слот, на который репозиторий реально ответил, — части, которые
   называет `request-idiom` для прямого вызова, то, что называют `event-addressing` и
   `event-payload-format` для сообщения, записи и поля из `data-stores`, и то, куда по
   `error-routing` попадает отклонение. Слот с ответом `none` ничего в этот блок не добавляет:
   не придумывай для него запись и никогда не называй протокол, хранилище или формат, которых в
   том файле нет. Если файла нет или нужных фактов в нём нет — остановись, спроси команду один
   раз и заполни его из `serpens/templates/testing-stack.md`. Один указатель на факт. `spns-test-plan`
   собирает payload'ы тестировщика из сценариев спеки и этого блока, поэтому пропущенная запись
   стоит тестировщику догадки.
   В delta-спеке СТРУКТУРНЫЕ ключевые слова остаются английскими — `## ADDED|MODIFIED|REMOVED|
   RENAMED Requirements` и `### Requirement: <текст>`, потому что openspec жёстко их зашивает.
   Текст требования и заголовки сценариев могут быть русскими: `#### Сценарий: …` допустим,
   выше по потоку считается любой заголовок 4-го уровня. У каждого ADDED и MODIFIED требования
   должен быть хотя бы один сценарий, а в тексте — SHALL или MUST.
   Выполни `<serpens-sdd> verify-docs` до зелёного. serpens-lint покрывает только то,
   чего не видит CLI: требование вне delta-секции, заголовок `### ` не в форме
   `### Requirement:` рядом с корректным, отсутствие `## Why` / `## What Changes` в proposal.md,
   плюс SHALL/MUST и наблюдаемость как предупреждения. Правило про сценарии и остальная
   delta-грамматика принадлежат CLI, поэтому одного зелёного verify-docs НЕ достаточно:
   `<openspec> validate <change-id> --type change --strict --json`. Правь до `"valid": true`;
   никогда не сдавай изменение, которое CLI отвергает.
   Добавь change folder в индекс ПО ПУТИ (`git add openspec/changes/<change-id>`), никогда
   `git add -A`: в репозитории есть локальные настройки и файлы с паролями, которые нельзя
   коммитить, а созданный тобой файл остаётся untracked, пока ты его не добавишь. Коммить
   `docs(<TICKET>): <текст>`, отправь ветку, открой или обнови spec PR и верни ссылку
   в историю. Аналитик не выполняет Git-операции.

4. НЕСКОЛЬКО РЕПОЗИТОРИЕВ — СНАЧАЛА TICKETS. Используй существующие дочерние
   tickets родительской истории и однозначно сопоставь каждый репозиторию. При
   пробеле остановись и спроси аналитика. Если дочерних tickets нет, уточни, кто
   создаёт по одному на репозиторий. Родительская история — ticket контракта
   хранилища; отдельный child для неё не нужен.

5. СНАЧАЛА КОНТРАКТ. ГДЕ ТЫ СТОИШЬ — ТУДА И ЛЯГУТ ФАЙЛЫ. Все пути ниже вычисляются через
   `git rev-parse --show-toplevel`, а зарегистрированный submodule — это отдельный git-корень,
   поэтому сначала `cd`, потом вычисление. Команда начинается в SYSTEM STORE: перейди туда, если
   ты не там, установи
   `STORE_ROOT="$(git rev-parse --show-toplevel)"` и выполни
   `<serpens-sdd> state prepare-base`. Возьми имя ветки стора для родительского тикета так же,
   как в шаге 3b (`git-naming --print-contract <parent-ticket>`), создай и опубликуй её, затем
   выполни
   `<serpens-sdd> state assert-change <parent-ticket>`.
   Выполни `<openspec> new change <contract-change-id>` (пропусти, если папка уже есть), затем
   `<serpens-sdd> state mark-change <contract-change-id> --ticket <parent-ticket>` — идемпотентно,
   возобновлённое изменение без метки её получит. Затем
   `<openspec> instructions proposal --change <contract-change-id> --json`. Прежде чем трогать
   `specs`, прочитай его состояние в `<openspec> status --change <contract-change-id> --json`:
   `skipped` значит, что `.openspec.yaml` этого изменения задаёт `skip_specs: true` — он
   ВЫПОЛНЕН, и создавать delta spec запрещено (собственный валидатор CLI отвергает изменение с
   `skip_specs: true`, у которого есть файлы спеки). Контракт стора без delta не задаёт форму,
   поэтому остановись и спроси аналитика, а не пиши её. Любое другое состояние — выполни
   `<openspec> instructions specs --change <contract-change-id> --json` — до proposal и contract delta.
   Они ложатся в собственный `openspec/changes/<contract-change-id>/` СТОРА: proposal.md,
   contract delta и research.md принадлежат стору, на ветке родительского тикета.
   Используй `store-contract.md`; форма живёт только здесь.
   В proposal контракта ОБЯЗАН быть буквальный заголовок `## Why` и буквальный `## What Changes`.
   Это не стиль: без `## Why` строка получения в каждом spoke падает с
   `{"code":"show_error","message":"Change must have a Why section"}`, при этом
   `validate --strict` даёт `"valid": true`, `status` и `list` работают, и ни один gate этого
   набора ничего не замечает. Контракт, который никто не может прочитать, хуже громкой ошибки,
   поэтому проверь сам до push:
   ```bash
   <openspec> show <contract-change-id> --type change --store <store-id> --json --deltas-only
   ```
   Должны появиться `"deltaCount"` и текст требования. Отсутствие `## Why` не обходится флагами:
   `--requirements-only`, `--no-scenarios` и устаревший `change show` падают так же.
   Выполни
   `<serpens-sdd> verify-docs` и
   `<openspec> validate <contract-change-id> --type change --strict --json`; правь, пока оба не
   зелёные и не `"valid": true`. Затем закоммить, отправь, открой PR и верни
   ссылку в parent.

6. ДЛЯ КАЖДОГО РЕПОЗИТОРИЯ, по одному. Каждый дочерний тикет принадлежит ровно одному
   репозиторию, и его артефакты живут ВНУТРИ этого репозитория, никогда в сторе:
   a. Сначала войди в submodule — `cd "$STORE_ROOT/submodules/<repo>"` — и только затем установи
      `REPO_ROOT="$(git rev-parse --show-toplevel)"`. Проверь: `REPO_ROOT` должен быть путём
      submodule, а не `STORE_ROOT`. Если они равны — ты всё ещё в сторе и все артефакты лягут не в
      тот репозиторий: остановись и сделай cd. Определись, где ты, точно как в шагах
      3b-3c, но с дочерним тикетом: спроси имя у `git-naming --print-contract <child-ticket>`, и
      если ты уже на ней — пропусти `prepare-base` и продолжай; если ветка есть локально или на origin — перейди на неё; и только если её нет нигде,
      выполни `<serpens-sdd> state prepare-base`, создай и опубликуй её.
      Заверши `<serpens-sdd> state assert-change <child-ticket>`. Дочерние
      тикеты приходят из шага 4, поэтому тикет здесь уже есть.
   b. Выполни `<openspec> new change <change-id>` изнутри submodule, чтобы папка изменения была
      собственной `openspec/changes/<change-id>/` этого репозитория (пропусти, если она есть), затем выполни
      `<serpens-sdd> state mark-change <change-id> --ticket <child-ticket>` — идемпотентно,
      возобновлённое изменение без метки её получит. Затем по одному
      сначала `<openspec> instructions proposal --change <change-id> --json`. Затем, ПРЕЖДЕ чем
      трогать `specs`, прочитай его состояние в `<openspec> status --change <change-id> --json`:
      `skipped` значит, что `.openspec.yaml` этого дочернего изменения задаёт `skip_specs: true`
      — законное «без изменений на уровне спеки», обычно рефакторинг потребителя без изменения
      поведения. Считай его ВЫПОЛНЕННЫМ, НЕ создавай delta spec (собственный валидатор CLI
      отвергает изменение с `skip_specs: true`, у которого есть файлы спеки), а указатели на
      контракт ниже положи в research.md. Возобновлённая ветка здесь — обычный случай:
      `new change` выше пропускается, когда папка уже есть, поэтому никогда не делай вывод
      «пропало» из папки, которую ты не создавал сам. Любое другое состояние — выполни
      `<openspec> instructions specs --change <change-id> --json` — только эти два — до proposal и
      собственной delta spec.
      Она ссылается на контракт, но не повторяет форму, и несёт ОБЕ строки получения: маршруты не
      пересекаются. Контракт стора мержится ПОСЛЕДНИМ, поэтому пока он открыт, он существует только
      внутри своей change-папки, а архивация удаляет эту папку ровно тогда, когда начинает работать
      spec-маршрут. Пиши обе строки с подписями и записывай рядом со spec id идентификатор
      CHANGE контракта: в открытом окне одного spec id недостаточно.
      ```text
      контракт: <contract-spec-id> в сторе <store-id> (change <contract-change-id>)
      пока change контракта открыт:
        <openspec> show <contract-change-id> --type change --store <store-id> --json --deltas-only
      после архивации change контракта:
        <openspec> show <contract-spec-id> --type spec --store <store-id>
      в каком я окне: <openspec> list --specs --store <store-id> — нет spec id, значит окно открыто
      если CLI отказывает (сломанный proposal контракта, незарегистрированный стор) — читай файл,
      но сначала прочитай состояние specs контракта: skipped значит, что delta читать нечего:
        <openspec> status --change <contract-change-id> --store <store-id> --json  # specs skipped => delta нет; спроси аналитика, не создавай
        <openspec> instructions specs --change <contract-change-id> --store <store-id> --json  # печатает changeDir
        cat <changeDir>/specs/<contract-spec-id>/spec.md
      ```
      `--json` на change-маршруте обязателен: без него CLI печатает только proposal.md, молча
      теряет delta и всё равно выходит с кодом 0. Никогда не используй здесь
      `<openspec> change show` или `<openspec> spec show`: у этих форм нет флага `--store`, они
      резолвятся в самом репозитории.
      В research.md сохраняй указатели. Не создавай design.md и tasks.md.
      Раздели факты тестировщика по владельцу. То, что это изменение ЗАДАЁТ — новый эндпоинт,
      новое поле, новая точка назначения, контракт ошибок — нормативно и живёт в delta-спеке, в
      тексте требования и его сценариях, где оно проходит ревью и попадает в архив. То, что
      изменение только ОБНАРУЖИВАЕТ в системе как она есть, идёт в research.md под заголовком
      `## OBSERVABLE CONTRACT` указателями.
      ЧТО ИМЕННО В ЭТОМ БЛОКЕ — это факт ЭТОГО репозитория, а не этой команды. Прочитай
      `serpens/testing-stack.md` и следуй его разделу `Ручной доступ для тестирования`: записывай по
      одному указателю на каждый слот, на который репозиторий реально ответил, — части, которые
      называет `request-idiom` для прямого вызова, то, что называют `event-addressing` и
      `event-payload-format` для сообщения, записи и поля из `data-stores`, и то, куда по
      `error-routing` попадает отклонение. Слот с ответом `none` ничего в этот блок не добавляет:
      не придумывай для него запись и никогда не называй протокол, хранилище или формат, которых
      в том файле нет. Если файла нет или нужных фактов в нём нет — остановись, спроси команду
      один раз и заполни его из `serpens/templates/testing-stack.md`. Один указатель на факт.
      `spns-test-plan` собирает payload'ы тестировщика из сценариев спеки и этого блока, поэтому
      пропущенная запись стоит тестировщику догадки.
   c. Выполни `<serpens-sdd> verify-docs`. При split-brain ошибке удали повтор формы
      и оставь ссылку. Затем выполни
      `<openspec> validate <change-id> --type change --strict --json`; правь до `"valid": true`.
   d. Добавь change folder по пути, коммит `docs(<child-ticket>): <текст>`, push, PR и ссылка
      в ticket. Никогда `git add -A`; не оставляй шаг незакоммиченным.

7. В каждом child зафиксируй порядок: согласовать контракт первым; реализовать
   producer первым; merge producer → consumers → контракт последним. Изменение
   контракта останавливает все репозитории. Child блокируется parent.

8. В parent опубликуй карту ticket → репозиторий → роль и окно merge.

9. До отчёта проверь: каждый child связан и сопоставлен; у каждого репозитория есть
   ветка, отправленный коммит и открытый PR; verify-docs зелёный и openspec `validate --strict`
   даёт `"valid": true`. Приложи доказательства.

# Serpens SDD — схема процесса поставки

> Схема на один экран. Полное описание процесса с таблицей по командам —
> [`FLOW.md`](FLOW.md), большая таблица по шагам — [`FLOW-TABLE.md`](FLOW-TABLE.md);
> установка — [`SETUP.md`](SETUP.md), обновление — [`UPGRADE.md`](UPGRADE.md),
> ежедневная работа — [`OPERATIONS.md`](OPERATIONS.md).

```text
Задача / запрос
  │
  ▼
1. СПЕЦИФИКАЦИЯ  — Аналитик, spns-spec
  вход:    только намерение либо задача + вики + действующая спецификация + текущий код
  сначала: если дано только намерение, уточнить его с пользователем до спецификации
  выход:   предложение + дельта-спецификация + исследование + ветка + коммит + pull request
  выходной критерий: проверки зелёные и `validate --type change --strict --json` отвечает
           "valid": true — во всех затронутых репозиториях
  │
  ▼
2. ПЛАН  — Разработчик, spns-plan
  вход:    одобренное изменение + текущий код
  выход:   design.md (<200 строк) + tasks.md с задачами по риску, закоммичены командой
  выходной критерий: проверки прошли; разработчик одобрил план
  │
  ▼
3. РЕАЛИЗАЦИЯ  — Разработчик, spns-implement
  цикл:    падающий сценарный тест → минимальное изменение → быстрые тесты → рефакторинг
  выход:   код + тесты + отмеченные задачи + результат запуска тестов, ОДНИМ коммитом в конце
  выходной критерий: все задачи завершены; полный набор и финальные проверки прошли; push сделан
  │
  ▼
4. РЕВЬЮ  — Ревьюер, spns-review
  проверки: покрытие → соответствие спецификации → честность тестов → корректность → скриптовые проверки
  выход:    замечания с серьёзностью, file:line и исправлением; либо чистый результат
  выходной критерий: блокирующие замечания исправлены; проверки запущены снова
  │
  ├─────────────────────────────┐
  ▼                             ▼
5. ПЛАН ЧЁРНОГО ЯЩИКА           6. ЗАГОТОВКИ АВТОТЕСТОВ
  вход: одобренные сценарии       вход: одобренные сценарии
  выход: выполнимый план в том    выход: по одному поведенческому тесту на сценарий
         же тикете                пометки: недостающая настройка остаётся TODO;
  учесть: регрессию и поиск сбоев;        запустить всё возможное
         расхождение спецификации и собранной системы ОСТАНАВЛИВАЕТ план
         и спрашивает пользователя: править дельту или заводить дефект
  └──────────────┬──────────────┘
                 ▼
7. АРХИВ ПОСЛЕ СЛИЯНИЯ  — Разработчик или ответственный за релиз, spns-archive
  вход:    слитый pull request + финальные доказательства
  выход:   действующие спецификации + ADR + индекс, коммитом `docs(<TICKET>): archive …`
  выходной критерий: слияние завершено; assert-archivable прошёл; записи сохранены
```

## Правила на каждом этапе

- Предложение OpenSpec, изменение спецификации и список задач — договор о поставке.
- Утверждение о завершении требует свежего доказательства.
- Несовпадение спецификации и кода останавливает работу до классификации причины.
- После изменений документации запускаются проверки репозитория: `verify-docs.sh`, который
  запускает проверку индекса, `serpens-lint.mjs` и проверку расхождений контрактов — последняя читает
  живые спецификации каждого хранилища И дельты с `store-contract.md` его активных changes, поэтому
  покрывает и межрепозиторное окно до архивации контракта.
- `serpens-lint.mjs` также отвергает незаполненный `port-facts.md`: `P`-строка, в которой ещё стоит
  шаблонный плейсхолдер `...`, или шаблонный заголовок `<port name + version> (probed YYYY-MM-DD)` —
  это ошибка, потому что из этого файла выводится вся установка.
- Каждый проверяющий режим `repository-state.sh` отказывает репозиторию, который не владеет
  собственным корнем OpenSpec (`✗ OpenSpec root is not this repository` · `↳ resolved root: <path>`);
  `inspect` лишь сообщает об этом. Проверка имени ветки идёт и на pre-commit, и на pre-push, потому
  что push новой ветки не несёт перечислимых файлов и lefthook пропускает pre-push копию.
- Грамматика дельта-спецификации — зона ответственности OpenSpec: каждая команда, которая пишет
  или проверяет спецификацию, запускает
  `<openspec> validate <change-id> --type change --strict --json`. Линтер оставляет себе только
  то, чего CLI не видит, — включая дельту `MODIFIED`/`REMOVED`/`RENAMED`, для которой нет живой
  спецификации: она проходит как `"valid": true` и падает только на `openspec archive`, после merge.
- Каждая команда сама доводит свою работу до коммита: добавляет файлы ПО ПУТЯМ, коммитит,
  делает push. Никогда `git add -A`.
- Люди одобряют планы, проводят ручное тестирование, принимают и сливают изменения; автоматизация не заявляет, что сделала это.

Создай каркасы автотестов для {{args}}.

КАКОЙ ФРЕЙМВОРК И ЧТО СЧИТАЕТСЯ БЫСТРЫМ ИЛИ МЕДЛЕННЫМ ТЕСТОМ — это факты ЭТОГО репозитория, а не
этой команды. Прочитай `serpens/testing-stack.md` и следуй ему. Если файла нет или нужных тебе
фактов в нём нет, остановись, спроси команду один раз и заполни его из
`serpens/templates/testing-stack.md`. Никогда не угадывай фреймворк, не выдумывай класс-харнесс и не
задавай человеку вопрос, на который этот файл уже отвечает. Раздел `Ручной доступ для
тестирования` в нём же говорит, до чего тест может дотянуться снаружи; ничего сверх этого
предполагать нельзя.

0. Установи `REPO_ROOT="$(git rev-parse --show-toplevel)"`. Выполни
   `<serpens-sdd> state assert-change <TICKET> --checkout --allow-dirty`.
   Остановись при неверной ветке истории или расхождении.
1. Один тест на сценарий, названный по нему и проверяющий поведение Given/When/Then,
   а не внутренние вызовы или private state.
2. Не выдумывай fixtures. Пометь данные и окружение как `TODO(<что нужно>)`.
3. Не читай и не меняй закрытые gate suites и их credentials. При такой задаче остановись.
4. Запусти всё доступное и приложи вывод. Незапускаемые каркасы пометь как drafts.
5. После записи OpenSpec или docs выполни `<serpens-sdd> verify-docs`.
6. ЗАКОММИТЬ написанные тесты.
   КОММИТЬ САМ — оператор не выполняет git за тебя, и шаг, который закончился незакоммиченной
   работой, не завершён. Добавляй в индекс ровно те файлы, которые ты написал, ПО ПУТИ
   (`git add <путь> …`). Никогда `git add -A`, `git add .` или `git commit -a`: в репозитории
   законно лежат локальные настройки, файлы с паролями и временный вывод, которые нельзя
   коммитить, а чужой untracked-файл — не твой. Созданный тобой файл остаётся untracked, пока ты
   его не добавишь: добавить его — часть работы по его написанию. Коммить сообщением
   `test(<TICKET>): <текст>` (тип и форму проверяет `<serpens-sdd> git-naming`, а
   `--print-contract` их печатает), отправляй в ветку истории и прикладывай вывод `git log --oneline -1` и `git status --short`.

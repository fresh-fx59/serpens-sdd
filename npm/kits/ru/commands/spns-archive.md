Архивируй изменение {{args}}. Следуй навыку spns-verification.
`<openspec>` — вызов CLI OpenSpec, подставленный при установке.
`{{args}}` — это `<change-id> [--here | --branch <имя>]`. Флаг выбирает, КУДА ляжет
коммит архивации; всё остальное — идентификатор изменения для архиватора.
0. Установи `REPO_ROOT="$(git rev-parse --show-toplevel)"`.
   Условие для любого режима: PR изменения смержен. Проверь это; если нет, спроси
   пользователя ОДИН раз — продолжать здесь или остановиться — и следуй ответу.
   Молча не останавливайся.
   Затем выбери место работы. Без флага спроси пользователя ОДИН раз, какой из трёх
   вариантов, покажи в вопросе текущую ветку и дождись ответа — сам не решай:
   - (1) свежая ветка истории от базы: выполни
     `<serpens-sdd> state prepare-base`, спроси имя у
     `<serpens-sdd> git-naming --print-contract <TICKET>` (поле `branch-example`), затем
     `git checkout -b "$BRANCH"` — пересоздай ветку истории, которую merge обычно удалил.
     Шаг 5 опубликует её и откроет PR. Бери напечатанное имя дословно: форма принадлежит команде,
     живёт в `serpens/branching.md`, и `<serpens-sdd> git-naming` принимает только её — имя,
     собранное вручную, или имя с суффиксом не проходит pre-push guard, и push отклоняется.
   - (2) ветка с твоим именем: то же самое, но имя обязано совпадать с тем, что печатает
     `--print-contract`.
   - (3) здесь: останься в текущей ветке и НЕ запускай `prepare-base`.
   Флаг отвечает на вопрос заранее и снимает его: `--branch <имя>` — это (2), `--here` — (3).
   Затем в любом режиме выполни `<serpens-sdd> state assert-archivable`;
   при ошибке остановись. Это доказывает, что дерево чистое, stash пуст и HEAD уже содержит
   настроенную базу, поэтому delta не может попасть в устаревшие спеки. Не предполагай, что
   база называется `main`, `master` или `develop`: инструмент определяет её сам.
   Если статус изменения показывает все артефакты в состоянии `done` ИЛИ `skipped`, а задачи —
   завершёнными, пропусти подтверждения по артефактам и задачам: `skipped` (например `specs`,
   когда `.openspec.yaml` изменения задаёт `skip_specs: true`) там тоже считается выполненным, а
   создавать пропущенный артефакт запрещено; проверка статуса уже дала ответ.
1. Выполни `<serpens-sdd> verify-docs`, затем
   `<openspec> validate <change-id> --type change --strict --json`; правь, пока verify-docs не
   зелёный, а CLI не даёт `"valid": true`. Грамматику delta-спеки проверяет CLI — линт её больше
   не дублирует. Заголовок не в форме `### Requirement: <текст>` — это ровно то, что
   `<openspec> archive` отвергает, падая посреди архивации, где восстановление ручное. Если delta корректна по смыслу, а архиватор всё равно отказывает,
   один раз спроси пользователя перед режимом `--no-validate`. Затем выполни
   `<openspec> archive <change-id> --yes --json` только с идентификатором изменения,
   без флага размещения.
   Delta перейдёт в `openspec/specs/`. У изменения с `skip_specs: true` переносить нечего —
   никогда не требуй delta spec — и CLI вернёт `"specsUpdated": false`; это ожидаемый успешный
   исход для такого изменения, а не сбой.
2. По решениям proposal, research.md и поправкам спеки создай ADR через
   `serpens/templates/adr.md` в `serpens/adr/NNNN-<slug>.md`. Принятые ADR не изменяй.
3. Запиши индекс: `<serpens-sdd> index`. Шаг обязателен: verify-docs
   запускает только `<serpens-sdd> index --check`, который показывает расхождение, но ничего не пишет.
4. Выполни `<serpens-sdd> verify-docs`; результат должен быть зелёным.
5. КОММИТЬ САМ — оператор не выполняет git за тебя, и шаг, который закончился незакоммиченной
   работой, не завершён. Добавляй в индекс ровно те файлы, которые дал этот шаг, ПО ПУТИ, И
   НАЗЫВАЙ ФАЙЛЫ ИНДЕКСА ЯВНО — `git add openspec/specs/<capability>/... serpens/adr/NNNN-<slug>.md
   serpens/index.json serpens/index.md serpens/repo.txt` (`repo.txt` только если шаг 3 создал
   его впервые) — никогда `git add -A` или `git add .`. Проверка индекса в verify-docs теперь
   отказывает на untracked или незастейдженном индексе (`checkIndexInGit`): пропущенный `git add`
   ловится, а не проходит незамеченным — но только для файлов, названных здесь явно, так что
   называй их явно, а не полагайся на более широкий `git add`. Коммить сообщением
   `docs(<TICKET>): archive {{args}} living spec and ADR`. Отправь текущую ветку.
   В режиме по умолчанию и `--branch` открой PR в настроенную базу; в режиме `--here` коммит
   уходит в существующий PR ветки. Каталог хранилища обновится при следующей агрегации;
   не правь его вручную.
6. Отправь короткую запись через настроенную интеграцию трекера. Если её нет,
   выведи готовый текст для ручной вставки.

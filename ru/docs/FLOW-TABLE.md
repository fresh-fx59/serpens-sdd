# Поток Serpens SDD — большая таблица

Эта таблица сопоставляет каждый шаг поставки истории с командой Serpens SDD, операцией
OpenSpec, принятой дисциплиной Superpowers, детерминированными скриптами и выходным условием.
Краткая версия тех же семи шагов — [`FLOW.md`](FLOW.md), схема — [`FLOW-SCHEMA.md`](FLOW-SCHEMA.md).

Все шесть навыков `spns-*` — корпоративные переработки, основанные на Superpowers; Serpens SDD
не запускает исходную среду Superpowers. Каждая команда начинается с детерминированной
проверки `repository-state.sh` на своём нумерованном шаге 0; каждый проверяющий режим этой
проверки (`prepare-base`, `assert-change`, `assert-archivable`) отказывает репозиторию, который не
владеет собственным корнем OpenSpec, с `✗ OpenSpec root is not this repository` и
`  ↳ resolved root: <path>`, а `inspect` лишь сообщает его в строке `openspec_root=`. Плейсхолдер OpenSpec во всём
комплекте ровно один — `<openspec>`, вызов CLI, который установка берёт из `port-facts.md`;
`<change-id>` — папка изменения. «Хук» означает, что пример конфигурации Lefthook установлен; он запускает
`check-git-naming.sh --branch` и на pre-commit, И на pre-push, потому что lefthook пропускает
pre-push команду, когда push не несёт файлов, которые он может перечислить, — это ровно тот push,
который публикует новую ветку.
«Проверки верификации» означают `verify-docs.sh` и три дочерних скрипта, которые он запускает:
`gen-index.mjs --check`, `serpens-lint.mjs` и `check-contract-split-brain.mjs` — последний снимает
отпечатки с живых спецификаций каждого связанного хранилища И с дельта-спецификаций и
`store-contract.md` его АКТИВНЫХ changes, поэтому он не слеп в межрепозиторном окне, ради которого
и существует.
Столбец ценности сравнивает покрытие рабочего процесса, а не измеренные результаты пилота.

Дельта спицы несёт ОБА подписанных маршрута получения, а не один: **пока change контракта открыт** — `<openspec> show <contract-change-id> --type change --store <store-id> --json --deltas-only` (`--json` обязателен; без него CLI печатает только proposal.md и всё равно выходит с 0) — и **после архивации change контракта** — `<openspec> show <contract-spec-id> --type spec --store <store-id>`. `<openspec> list --specs --store <store-id>` отвечает, в каком ты окне: отсутствие spec id значит, что change ещё открыт. ## Быстрое подключение продуктовой команды

Подключение рассчитано на быстрый, простой и безопасный старт: без масштабной миграции и необходимости заранее описывать всю унаследованную систему. Первым результатом должно стать реальное поставленное изменение, а не проект по документированию. Фактические сроки должны быть подтверждены пилотом.

1. Выбрать одну продуктовую команду, 2–3 связанных репозитория и небольшое реальное изменение.
2. Один раз установить общий комплект Serpens SDD и дать каждой роли короткий понятный сценарий работы.
3. Выполнить пилот, не заменяя действующие инструменты, роли, ревью или процесс тестирования команды.
4. Сравнить с исходным уровнем понятность, длительность цикла, количество дефектов, усилия на ревью и отзывы команды.
5. Устранить выявленные препятствия, затем по желанию подключать следующие команды; сохранить возможность отката.

## Вспомогательная автоматизация за пределами семи шагов поставки

Эти скрипты есть в стартовом комплекте, но текущие тела семи команд не вызывают их напрямую:

- `check-openspec-root.sh` проверяет, что OpenSpec указывает на текущий Git-репозиторий. Руководство по настройке требует выполнить его до работы со спецификацией, но `spns-spec` сейчас его не вызывает.
- `sync-submodules.sh` регистрирует, инициализирует и проверяет репозитории, перечисленные системным хранилищем, как Git-подмодули в `system-store/submodules/`; он только добавляет и никогда не удаляет привязку. `aggregate-index.mjs` создаёт компактный межрепозиторный каталог возможностей.
- `index-all.sh` создаёт необязательный индекс поиска кода Zoekt по этим подмодулям и завершается ошибкой, если для индексации символов отсутствует Universal Ctags.
- `kit-version.sh` отвечает на вопрос «из какой редакции комплекта этот файл?» — режимы `show`, `list`, `check`, `verify` по `MANIFEST.sha256` и `identify <installed-file>` с вердиктом pristine / MODIFIED / UNSTAMPED. `UPGRADE.md` запускает его до того, как что-либо трогать.

Две границы стоит назвать прямо, потому что раньше они были размыты:

- **Грамматика дельта-спецификации принадлежит OpenSpec.** `serpens-lint.mjs` больше не перепроверяет то, на что уже ругается `validate --type change --strict --json`. Он оставляет себе только слепые зоны: заголовок требования вне любой дельта-секции (upstream молча его выбрасывает), опечатку в заголовке `### ` рядом с правильным (upstream пишет INFO и выбрасывает это требование), `proposal.md` без дословного заголовка `## Why` или `## What Changes` (upstream оставляет `"valid": true`, а его собственный ридер падает с `Change must have a Why section`), дельту `MODIFIED`/`REMOVED`/`RENAMED` на capability, у которой нет `openspec/specs/<id>/spec.md` (upstream сообщает `"valid": true`, а затем `openspec archive` падает уже после merge с `archive_spec_update_failed: "<id>: target spec does not exist; only ADDED requirements are allowed for new specs. MODIFIED and RENAMED operations require an existing spec."`), рекомендацию про SHALL/MUST и предупреждение о наблюдаемой поверхности.
- **`port-facts.md` не только пишут, но и читают.** `port-facts.md` в хранилище записывает домашний каталог агента, имя файла инструкций проекта, закреплённый вызов CLI и идентификаторы — из него выводится вся установка. `serpens-lint.mjs` жёстко падает на копии, где в `P`-строке ещё стоит шаблонный плейсхолдер `...` или в заголовке остался шаблон `<port name + version> (probed YYYY-MM-DD)`: незаполненный опрос порта не может дойти до зелёного `verify-docs.sh`.
- **Домашний каталог агента определяется, а не задаётся.** `serpens-lint.mjs` берёт его из `SERPENS_AGENT_DIR`, иначе из `git config serpens.agentDir`, иначе — единственный точечный каталог в корне репозитория, внутри которого есть подкаталог `skills/`. Имя каталога ни одного порта нигде не зашито.

Файлы команд и навыков — это шаблоны для корпоративной версии интерфейса агента. Вызов `<openspec>`, инструменты трекера и wiki, автоматизация pull request и собственный `docs/testing-stack.md` репозитория должны быть зафиксированы и проверены на этапе исследования возможностей этой версии.

# Serpens SDD flow — the wide table

This table maps each story-delivery step to its Serpens SDD command, OpenSpec operation,
adopted Superpowers discipline, deterministic scripts, and exit gate.
The short version of the same seven steps is [`FLOW.md`](FLOW.md); the diagram is
[`FLOW-SCHEMA.md`](FLOW-SCHEMA.md).

All six `spns-*` skills are corporate rewrites derived from Superpowers; Serpens SDD does
not invoke an upstream Superpowers runtime. Every command starts with the deterministic
`repository-state.sh` gate at its numbered step 0; every asserting mode of that gate
(`prepare-base`, `assert-change`, `assert-archivable`) refuses a repository that does not own its
own OpenSpec root with `✗ OpenSpec root is not this repository` and `  ↳ resolved root: <path>`,
while `inspect` only reports it on its `openspec_root=` line. There is ONE OpenSpec placeholder in the whole
kit — `<openspec>`, the CLI invocation setup resolves from `port-facts.md` — and `<change-id>` is
the change folder. “Hook” means the example Lefthook configuration has been installed; it runs
`check-git-naming.sh --branch` at pre-commit AND pre-push, because lefthook skips a pre-push
command when the push carries no files it can list — exactly the push that publishes a new branch.
“Verification checks” means `verify-docs.sh` and the three child scripts it runs:
`gen-index.mjs --check`, `serpens-lint.mjs`, and `check-contract-split-brain.mjs` — which
fingerprints each referenced store's living specs AND the delta specs and `store-contract.md` of
its ACTIVE changes, so it is not blind during the cross-repo window it exists to protect.
The value column compares workflow coverage, not measured pilot outcomes.

| 1. Specify the change<br>Analyst · `spns-spec` | Reads the tracker story, wiki, living specs, and live code; interviews ONCE at story level; chooses single-repository or cross-repository shape; places itself on the story branch before creating anything; creates branches, commits, pull requests, and tracker links. Cross-repository work creates the shared contract in the STORE first, then one linked change per repository — inside that repository. | `<openspec> new change <change-id>` (skipped when the folder exists), then one artifact at a time: `<openspec> instructions proposal --change <change-id> --json` and `<openspec> instructions specs --change <change-id> --json`. `design` and `tasks` belong to `spns-plan`. ## Fast product-team onboarding

Onboarding is designed to be fast, easy, and low-risk: no big-bang migration and no need to document the entire legacy system first. The first result is a real delivered change, not a documentation project. Actual timing must be confirmed by the pilot.

1. Select one product team, 2–3 related repositories, and one small real change.
2. Install the shared Serpens SDD kit once and give each role a short guided flow.
3. Deliver the pilot without replacing the team's existing tools, roles, review, or testing process.
4. Compare clarity, cycle time, defects, review effort, and team feedback with the baseline.
5. Remove any friction, then expand to the next teams by opt-in; keep a rollback path.

## Supporting automation outside the seven story steps

These scripts exist in the starter kit but are not invoked directly by the current seven
command bodies:

- `check-openspec-root.sh` verifies that OpenSpec resolves to the current Git repository. The
  setup runbook requires it before spec work, but `spns-spec` does not currently call it.
- `sync-submodules.sh` registers, initializes, and validates the repositories listed by the system
  store as Git submodules under `system-store/submodules/`; it adds only and never deletes a binding. `aggregate-index.mjs` builds its thin cross-repository capability catalog.
- `index-all.sh` builds the optional Zoekt code-search index over those submodules and fails if symbol indexing
  lacks Universal Ctags.
- `kit-version.sh` answers "which kit edition is this file from?" — `show`, `list`, `check`,
  `verify` against `MANIFEST.sha256`, and `identify <installed-file>` reporting
  pristine / MODIFIED / UNSTAMPED. `UPGRADE.md` runs it before touching anything.

Two boundaries are worth stating because they used to be blurred:

- **OpenSpec owns delta-spec grammar.** `serpens-lint.mjs` no longer re-checks what
  `validate --type change --strict --json` already errors on. It keeps only the blind spots: a
  requirement heading outside any delta section (upstream drops it silently), a mistyped `### `
  heading standing beside a good one (upstream logs INFO and drops that requirement), a
  `proposal.md` with no literal `## Why` or `## What Changes` heading (upstream keeps
  `"valid": true` while its own reader fails with `Change must have a Why section`), a
  `MODIFIED`/`REMOVED`/`RENAMED` delta whose capability has no `openspec/specs/<id>/spec.md`
  (upstream reports `"valid": true`, then `openspec archive` fails post-merge with
  `archive_spec_update_failed: "<id>: target spec does not exist; only ADDED requirements are
  allowed for new specs. MODIFIED and RENAMED operations require an existing spec."`), the
  SHALL/MUST advisory, and the observable-surface warning.
- **`port-facts.md` is read, not just written.** The store's `port-facts.md` records the agent
  home, the project instruction filename, the pinned CLI invocation and the ids — the whole
  install derives from it. `serpens-lint.mjs` hard-fails on a copy that still holds the template
  placeholder `...` in a `P`-row, or the template header `<port name + version> (probed
  YYYY-MM-DD)`, so an unfilled port probe cannot reach a green `verify-docs.sh`.
- **The agent home is discovered, never named.** `serpens-lint.mjs` resolves it from
  `SERPENS_AGENT_DIR`, else `git config serpens.agentDir`, else the single root dot-directory that
  contains a `skills/` subdirectory — so no port's directory name is hard-coded anywhere.

The command and skill files are templates for a corporate agent CLI port. The `<openspec>`
invocation, tracker and wiki tools, pull-request automation, and the repository's own
`docs/testing-stack.md` must be pinned and proven during that port's discovery step.

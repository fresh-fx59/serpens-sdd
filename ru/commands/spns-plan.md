description: Создать design и tasks утверждённого изменения по текущему коду
serpens-version: 2026-09-25.1

Спланируй {{args}}. Следуй spns-drill-down и spns-verification.
`{{args}}` — это `<change-id>`; `<openspec>` — вызов CLI OpenSpec, подставленный при установке.
Условия — ДВА независимых требования, оба обязательны. Одно не заменяет другое.
(а) АРТЕФАКТЫ ГОТОВЫ. `<openspec> status --change <change-id> --json` должен показывать `design`
как `ready` (или уже `done`) — никогда `blocked`. Артефакт перед ним со статусом `skipped`
(например `specs`, когда `.openspec.yaml` изменения задаёт `skip_specs: true`) считается
выполненным, а не пропущенным — создавать `skipped`-артефакт запрещено, CLI сам это отвергает.
Если `design` в статусе `blocked`, остановись и назови артефакт из его `missingDeps` и его
собственное состояние.
(б) PROPOSAL УТВЕРЖДЁН. Proposal этого изменения должен быть УТВЕРЖДЁН аналитиком. Статус
артефакта — это готовность, то есть выполнены ли зависимости; согласие человека он никогда не
фиксирует, и CLI об этом не знает — проверь историю. Если proposal не утверждён, остановись и
скажи об этом.
0. Установи `REPO_ROOT="$(git rev-parse --show-toplevel)"`. Выполни
   `<serpens-sdd> state assert-change <TICKET> --checkout`; при ошибке остановись.
   `--checkout` переключает на ветку истории, если ты не на ней, а она уже есть — локально или на
   origin. Он никогда её не создаёт: «does not exist locally or on origin» значит сначала `spns-spec`.
   Дальше спрашивай CLI по ОДНОМУ артефакту. `<openspec> status --change <change-id> --json` —
   источник истины о том, какие артефакты нужны этой схеме и в каком они состоянии; никогда не
   считай список идентификаторов зафиксированным. Эта команда владеет ровно `design` и `tasks` —
   теми двумя, которые не создаёт `spns-spec`. Артефакт со статусом `skipped` не требует файла —
   создавать его запрещено (CLI отвергает delta spec у изменения с `skip_specs: true`), поэтому
   сначала читай статус, а не предполагай пропажу:
   ```bash
   <openspec> instructions design --change <change-id> --json
   <openspec> instructions tasks  --change <change-id> --json
   ```
   Каждый вызов возвращает указания и точный путь вывода для этого артефакта; напиши его и переходи
   к следующему. Других артефактов не создавай и к реализации не переходи.
0. ПРОВЕРКА СХЕМЫ, всегда первой. Выполните `<serpens-sdd> check-schema`. Если код возврата не ноль, ОСТАНОВИТЕСЬ — не читайте дальше, ничего не создавайте — и передайте аналитику вывод команды дословно; он называет неподдерживаемую схему, точное место, где она найдена, и то, что поддержка отложена (см. spec-skipspecs-and-custom-schemas-2026-09-11.md, пункт 4b).

1. Прочитай delta spec (у изменения с `skip_specs: true` его нет — пропусти этот источник,
   никогда не создавай его), research.md, изменяемые живые спеки и текущий код модулей.
2. Напиши design.md: подход, файлы и классы, точки интеграции и риски, и по одной строке на каждый
   сценарий приёмки — какая наблюдаемая поверхность его реализует (те поверхности и хранилища,
   которые называет `serpens/testing-stack.md`).
   Именно эта строка ведёт `spns-test-plan` от спеки к стенду. Не более 200 строк.
3. Напиши tasks.md. Первая строка — состояние и следующая задача. Каждая задача — один
   проверяемый red-green цикл со сценарием, тестом и областью кода. Рискованное — первым.
4. Выполни `<serpens-sdd> verify-docs`; исправь всё до зелёного.
5. ЗАКОММИТЬ design.md и tasks.md.
   КОММИТЬ САМ — оператор не выполняет git за тебя, и шаг, который закончился незакоммиченной
   работой, не завершён. Добавляй в индекс ровно те файлы, которые ты написал, ПО ПУТИ
   (`git add <путь> …`). Никогда `git add -A`, `git add .` или `git commit -a`: в репозитории
   законно лежат локальные настройки, файлы с паролями и временный вывод, которые нельзя
   коммитить, а чужой untracked-файл — не твой. Созданный тобой файл остаётся untracked, пока ты
   его не добавишь: добавить его — часть работы по его написанию. Коммить сообщением
   `docs(<TICKET>): <текст>` (тип и форму проверяет `<serpens-sdd> git-naming`, а
   `--print-contract` их печатает), отправляй в ветку истории и прикладывай вывод `git log --oneline -1` и `git status --short`.
6. Представь план разработчику для утверждения. Не начинай реализацию.

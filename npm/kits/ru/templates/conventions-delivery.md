# Соглашения по доставке (delivery)

**Место:** `system-store/serpens/delivery.md`. Единственный источник правды для всего хозяйства.
Репозитории и агенты читают его через `serpens-sdd delivery --print-contract` / `--handoff`, а не
пересказывают значения в своей прозе.
**Проверяется:** `serpens/bin/serpens-sdd delivery`, а также `state assert-archivable` для
проверки архивации, ключуемой `merge-style`. Промпты советуют, проверки принуждают — никогда не
чините красную проверку её ослаблением.

## Что это охватывает

Слово форджа (PR vs MR), кто открывает pull/merge request, топологию тикетов, куда постятся план и
тест-план, порядок утверждения, порядок и стиль мержа, границу ревью, интеграционную и релизную
ветку, когда запускается архивация, и куда уходит передача (hand-off). Вне охвата: форма
веток/коммитов (`branching.md`), названия ролей, названия окружений.

## Как изменить форму под свою команду

Значения ниже — встроенное значение по умолчанию, сегодняшнее поведение кита, неизменное, пока вы
не добавите блок контракта. Скопируйте это, уберите из блока кода и подставьте свои значения:

```markdown
<!-- serpens:section delivery-contract -->
| Field | Value |
|---|---|
| `forge-word`          | PR |
| `pr-opened-by`        | human |
| `ticket-topology`     | parent-story+child-per-repo |
| `child-created-by`    | ask |
| `proposal-approval`   | analyst-in-story |
| `test-plan-posted-to` | same-ticket-comment |
| `merge-order`         | producer,consumers,store-contract |
| `review-may-merge`    | no |
| `integration-branch`  | develop |
| `release-branch`      | master |
| `archive-when`        | after-qa-accepted |
| `merge-style`         | merge |
| `handoff-to`          | chat |
```

- Блок НЕ должен лежать внутри блока кода — ограждение его прячет, и именно поэтому пример выше
  остаётся примером.
- Любая ошибка внутри блока — жёсткая остановка с именем этого файла и номером строки. Молчаливого
  отката к значениям по умолчанию нет.
- Посмотреть, что действует прямо сейчас:

```bash
serpens-sdd delivery --print-contract
serpens-sdd delivery --handoff [--change <change-id>] [--base <branch>]
```

`--handoff` записывает переданный tip (T, последний РАБОЧИЙ коммит — никогда сам коммит записи
передачи), а затем сам коммитит и пушит ЭТУ ЗАПИСЬ своим собственным коммитом
`chore(<TICKET>): record handoff <sha>` — дерево никогда не остаётся грязным. `--change
<change-id>` называет, к какому изменению относится передача; без него инструмент выводит тикет
из имени текущей ветки и находит помеченное для него изменение (`state mark-change`). Повторная
передача для того же изменения (после более раннего squash/merge) дописывает новую запись;
последняя побеждает для проверки мержа, более ранние сохраняются для запасного варианта squash.

## Справочник настроек

Каждое поле ниже: что оно контролирует, зачем оно существует, список допустимых значений с
однострочным пояснением, и значение по умолчанию.

- **`forge-word`** — слово, которым проза кита называет запрос на изменение. Не даёт киту
  говорить «PR» в команде, где это называется «MR».
  - `PR` — формулировка pull request. **По умолчанию.**
  - `MR` — формулировка merge request.

- **`pr-opened-by`** — кто открывает запрос на изменение. Не даёт агенту пытаться выполнить
  действие форджа (`gh pr create`, `glab mr create`, вызов API форджа) в команде, где это может
  делать только человек.
  - `human` — агент только коммитит и пушит; он никогда не пытается создать PR/MR. Вместо этого
    он печатает передачу (`delivery --handoff`). **По умолчанию**, и это же окружение автора кита.
  - `agent` — агент может сам открыть PR/MR.

- **`ticket-topology`** — как тикетится изменение, затрагивающее несколько репозиториев. Не даёт
  агенту придумывать свою форму тикетов для каждой команды.
  - `parent-story+child-per-repo` — одна родительская история с общим контрактом, один дочерний
    тикет на репозиторий, который его реализует. **По умолчанию**, и единственное поставляемое
    значение — `single-ticket` отложено (см. Отложенное ниже), это не рабочая опция.

- **`child-created-by`** — кто создаёт дочерние тикеты по репозиториям под родительской историей.
  Не даёт агенту молча решать это самому.
  - `ask` — агент каждый раз спрашивает человека. **По умолчанию.**
  - `analyst` — аналитик создаёт дочерние тикеты; агент ждёт, пока они появятся.
  - `agent` — агент сам создаёт дочерние тикеты (нужен доступ на запись в трекер).

- **`proposal-approval`** — кто должен утвердить предложение спецификации до начала планирования.
  Не даёт `spns-plan` стартовать по неутверждённой идее.
  - `analyst-in-story` — аналитик утверждает предложение внутри тикета истории. **По умолчанию.**
  - `none` — утверждение предложения не требуется; планирование может начаться сразу.

- **`test-plan-posted-to`** — куда записывается тест-план. Не даёт появиться второму, никем не
  просматриваемому тикету теста.
  - `same-ticket-comment` — постится комментарием в тот же тикет, где ведётся работа. **По
    умолчанию.**
  - `print-only` — печатается только в чат; запись в трекер не происходит (используется, когда
    трекер не настроен).

- **`merge-order`** — порядок мержа репозиториев для изменения, затрагивающего несколько
  репозиториев с общим контрактом. Не даёт потребителю смержиться раньше своего производителя, а
  контракту стора — раньше обоих.
  - список через запятую, перестановка `producer,consumers,store-contract` — те же три токена в
    порядке, который отражает реальное направление зависимостей вашей команды.
  - **По умолчанию:** `producer,consumers,store-contract` (сначала производитель, контракт стора
    — последним).

- **`review-may-merge`** — может ли ревьюер также мержить. Оставлено видимым полем с одним
  значением, а не тихо предполагается, чтобы граница была явной.
  - `no` — единственное допустимое значение; ревью никогда не мержит. **По умолчанию**, и
    единственное поставляемое значение (любое другое значение — ошибка конфигурации намеренно:
    эту границу нельзя ослабить настройкой).

- **`integration-branch`** — ветка, в которую мержатся feature-ветки (`develop` в git-flow, или
  свой trunk команды). Питает разрешение базовой ветки, которое использует инструмент проверки состояния репозитория, и проверку архивации,
  ключуемую `merge-style`.
  - любое допустимое имя ветки (`git check-ref-format --branch`). **По умолчанию, если не
    задано:** сегодняшний порядок определения — `origin/develop`, если существует, иначе
    символический HEAD удалённого репозитория (та же логика, которую кит уже
    использовал; это поле лишь переопределяет определение, новое поведение не вводится, пока оно
    не задано).

- **`release-branch`** — ветка, в которую вырезается релиз (`master`/`main` в git-flow). Только
  информационное: сегодня ни один шлюз его не читает; оно питает текст передачи/статуса
  (рекомендации по релизному PR).
  - любое допустимое имя ветки. **По умолчанию:** `master`.

- **`archive-when`** — когда шаг 0 `spns-archive` вообще может запуститься. Не даёт заархивировать
  изменение раньше реального момента «оно и правда доставлено» для этой команды.
  - `after-merge` — архивация сразу после мержа feature-ветки в `integration-branch`.
  - `after-qa-accepted` — архивация ждёт, пока тестировщик подтвердит развёрнутую интеграционную
    ветку. **По умолчанию** — человек должен подтвердить этот выбор один раз на всё хозяйство;
    агент спрашивает, никогда не предполагает, и записывает ответ.

- **`merge-style`** — как мержи попадают в `integration-branch`, чтобы шлюз архивации мог отличить
  «мои коммиты реально попали туда» от устаревшего суррогата. Обязателен, как только подключена
  проверка мержа — молчаливого значения по умолчанию нет, потому что логика проверки разная для
  каждого значения.
  Как только `merge-style` задан, `state assert-archivable` требует `--change <change-id>`:
  handoff-tip хранится ПО ИЗМЕНЕНИЮ, никогда по ветке — ветка истории, на которой была передача,
  к моменту архивации обычно удалена, и архивация может выполняться на любой ветке (часто прямо
  на `integration-branch`). Передача, записанная во время `spns-implement`/`spns-spec` (изменение
  ещё помечено, `openspec/changes/<change-id>/` ещё существует), привязана к этому change-id;
  записанная позже, после того как `<openspec> archive` свернул изменение, использует сам тикет
  как ключ — но всё равно никогда не ветку.
  - `merge` — настоящий merge-коммит; проверяется тем, что «записанный SHA переданного tip —
    предок `origin/<integration-branch>`».
  - `squash` — squash в один коммит на интеграционной ветке; проверяется совпадением набора путей
    (изменённые пути tip совпадают с изменёнными путями диффа интеграционной ветки), так как сам
    исходный коммит исчезает.
  - `rebase` — переигран коммит за коммитом; проверяется через `git cherry` (каждый коммит с tip
    уже применён, строк `+` нет).
  - **Значения по умолчанию нет** — должно быть задано явно, как только в хозяйстве подключена
    проверка мержа.

- **`handoff-to`** — куда уходит вывод `delivery --handoff`, помимо того, что он всегда печатается
  в чат. Не даёт передаче молча пропасть в команде, где её ожидают увидеть ещё и в тикете.
  - `chat` — печатается только в чат. **По умолчанию.**
  - `chat+ticket` — также постится комментарием в тикет (тот же тикет, в который целится
    `test-plan-posted-to`). Требует настроенного трекера; если трекер не настроен, это ошибка с
    именем недостающего трекера, а не молчаливый откат к `chat`.

## Отложенное (не поставляется, сегодня не допустимое значение)

- **`ticket-topology=single-ticket`** — ни одна команда этого не просила. Два случая, которые оно
  вроде бы покрывало, уже работают без него: изменению в одном репозитории никогда не был нужен
  родитель/тикет контракта стора, а изменение в нескольких репозиториях без настоящего общего
  контракта планируется как N независимых историй, по одной на репозиторий. Реальная потребность
  «один тикет, много репозиториев, без разбивки по репозиториям» — это новое значение перечисления,
  предложенное и протестированное само по себе, а не воскрешение этого отложенного.

## `## Team notes`

Свободный текст ниже этого якоря показывается агенту как контекст (особенности хозяйства, этикет
передачи, всё, что человек хочет запомнить). Ни один шлюз или тест от него не зависит — парсер
полностью его игнорирует, как и любую прозу вне заякоренной/ограждённой таблицы.

## Архивация: механическая, независимо от того, кто открывает PR

Предусловие архивации всегда проверяется командой `serpens-sdd state assert-archivable --change
<change-id>`, никогда чтением UI форджа, трекера или ссылки на PR. Ненулевой код выхода = не
смержено. Кто открыл PR/MR не меняет проверку — она читает только git. Всегда передавай
`--change`: проверка, ключуемая `merge-style`, читает handoff-tip, записанный для ЭТОГО изменения,
а не для той ветки, на которой ты сейчас стоишь.

**Отказ всегда обоснован — никогда не обходи его.** При `merge-style=merge`/`rebase` проверка
также требует, чтобы запись хранила commit-trailer `Serpens-Handoff-Tip:`, который создаёт только
`delivery --handoff`; запись без него отклоняется как непроверяемая, даже если строка
`handoff-tip:` выглядит правильно. Никогда не редактируй `.serpens.yaml` вручную, не выдумывай
строку `handoff-tip:` и не создавай коммит `chore(<TICKET>): record handoff <sha>` сам, чтобы
пройти проверку — именно эту подделку и обнаруживает trailer. Если отказ кажется ошибочным,
скажи об этом человеку точным сообщением инструмента; не обходи проверку.

## Кто что делает

- **Агент** читает контракт этого файла через `serpens-sdd delivery --print-contract` перед каждым
  моментом «открой PR», и через `serpens-sdd delivery --handoff`, когда `pr-opened-by=human` — он
  никогда не собирает текст передачи сам.
- **DevOps** владеет этим файлом. Изменение здесь — это изменение во всех репозиториях.

---
description: Реализовать текущее изменение по задачам с дисциплиной TDD
serpens-version: 2026-09-23.1
---
Реализуй изменение {{args}}. Следуй spns-tdd, spns-verification, spns-debugging и spns-drill-down.
`{{args}}` — это `<change-id>`; `<openspec>` — вызов CLI OpenSpec, подставленный при установке.
0. Установи `REPO_ROOT="$(git rev-parse --show-toplevel)"`. Выполни
   `<serpens-sdd> state assert-change <TICKET> --checkout --allow-dirty`.
   Он переключит на ветку истории, если ты не на ней, а она есть; создавать её он не будет.
   Остановись при неверной ветке, отсутствии upstream или расхождении. Затем выполни
   `<openspec> instructions apply --change <change-id> --json` и прочитай состояние задач:
   `state`, `progress`, `tasks`, `contextFiles`. Артефакт со статусом `skipped` (например
   `specs`, когда `.openspec.yaml` изменения задаёт `skip_specs: true`) там уже считается
   выполненным — никогда не создавай его. Состояние `blocked` значит, что не хватает чего-то
   ДРУГОГО: остановись и запусти `spns-plan`. Это источник состояния, а не инструкций:
   главным остаётся цикл Serpens TDD ниже.
0. ПРОВЕРКА СХЕМЫ, всегда первой. Выполните `<serpens-sdd> check-schema`. Если код возврата не ноль, ОСТАНОВИТЕСЬ — не читайте дальше, ничего не создавайте — и передайте аналитику вывод команды дословно; он называет неподдерживаемую схему, точное место, где она найдена, и то, что поддержка отложена (см. spec-skipspecs-and-custom-schemas-2026-09-11.md, пункт 4b).

1. Сначала прочитай заголовок состояния tasks.md и research.md; продолжай, не выводи заново.
2. Если design.md или tasks.md отсутствуют либо устарели, пересоздай их по текущему коду.
3. На задачу: падающий тест из сценария → минимум кода → запуск → доказательство в
   tasks.md → checkbox → новое состояние. Не коммить по каждой задаче.
   ПИШИ ФАЙЛЫ НАПРЯМУЮ: `cat > <path> <<'EOF'` … `EOF`, один файл на команду. Если запись
   падает из-за кавычек, повтори её мельче (раздели файл или `printf '%s\n' 'строка' … > <path>`).
   Никогда не пиши вспомогательный скрипт (`/tmp/x.mjs`, `.py`, `.sh`) и не запускай его, чтобы
   создать файлы: запуск своего скрипта — запрещённое действие, даже если он только пишет файл.
   Медленные тесты запускай на границе задачи.
4. При конфликте спеки и кода — включая сценарий приёмки, который больше не наблюдаем как записан —
   остановись: если delta spec существует, вынеси в неё поправку и проверь
   `<openspec> validate <change-id> --type change --strict --json` до `"valid": true`, сообщи
   аналитику через трекер и жди; если изменение задаёт `skip_specs: true`, поправлять НЕЧЕГО —
   создавать delta spec запрещено — сообщи аналитику через трекер и жди так же;
   неожиданный код исследуй и перепланируй; нереализуемое требование эскалируй.
5. После каждой записи в openspec/ или docs/ выполни
   `<serpens-sdd> verify-docs`.
6. ЗАКОММИТЬ ВСЮ РАБОТУ ОДИН РАЗ, когда закрыты все задачи, — не по задаче. Оператор не
   выполняет git за тебя, и реализация с незакоммиченной работой не завершена. Добавляй в индекс
   ровно те файлы, которые дало это изменение, ПО ПУТИ (`git add <путь> …`). Никогда
   `git add -A`, `git add .` или `git commit -a`: в репозитории законно лежат локальные
   настройки, файлы с паролями и временный вывод, которые нельзя коммитить, а чужой
   untracked-файл — не твой. Созданный тобой файл остаётся untracked, пока ты его не добавишь.
   Форма темы коммита и список типов принадлежат команде, а не тебе:
   `<serpens-sdd> git-naming --print-contract <TICKET>` печатает `commit-form`, `commit-types` и
   готовый `commit-example`. Пиши тему в этой форме (`feat` для функции, `fix` для дефекта),
   отправляй в ветку истории. Дальше по `<serpens-sdd> delivery --print-contract`: если
   `pr-opened-by=human` — выполни `<serpens-sdd> delivery --handoff --change <change-id>` и
   вставь его вывод человеку дословно, НЕ создавай change request; эта команда записывает tip
   этого push и сама коммитит + пушит запись, привязанную к `<change-id>`, так что более поздний
   `state assert-archivable --change <change-id>` найдёт её независимо от того, на какой ветке он
   выполняется. Если `agent` — открой или обнови его сам. Приложи вывод
   `git log --oneline -1` и `git status --short`.
7. Готово только при закрытых задачах, зелёном полном наборе тестов, verify-docs и
   закоммиченной отправленной работе. Приложи свежий вывод последнего запуска.

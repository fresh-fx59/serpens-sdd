# Эксплуатация

## Ежедневная входная проверка

Начинайте внутри выбранного репозитория, а не в корне системного хранилища:

```bash
export REPO_ROOT="$(git rev-parse --show-toplevel)"
<serpens-sdd> state inspect
```

Перед новой историей выполните `prepare-base`, спросите имя ветки у
`<serpens-sdd> git-naming --print-contract <TICKET>`, создайте её от показанной базовой ветки,
опубликуйте upstream и выполните `assert-change <TICKET>`. Форма ветки и коммита принадлежит
команде: она живёт в `serpens/branching.md`, и ни один файл этого набора её не дублирует.
При продолжении прерванной работы используйте `--allow-dirty` только после проверки
каждого локального изменения. Ненулевой код — жёсткая остановка.

Инструмент не делает reset, clean, rebase, не удаляет ветки, не меняет неизвестное
грязное дерево и не скрывает локальные коммиты. База определяется по
`SERPENS_BASE_BRANCH`, локальному `serpens.baseBranch`, `.gitmodules` родительского
хранилища, удалённому `develop`, затем удалённой ветке по умолчанию.

`<serpens-sdd> state inspect` печатает `dirty=` и `untracked=` как два отдельных факта, и
только первый что-то блокирует. `dirty` считает незакоммиченные изменения ОТСЛЕЖИВАЕМЫХ файлов
(`--porcelain --untracked-files=no --ignore-submodules=untracked`). Untracked-файлы — локальные
настройки, файлы с паролями, вывод сборки — выводятся предупреждением и не блокируют ничего,
поэтому рабочий репозиторий не нужно вычищать перед командой spns-*. В сторе submodule, у
которого изменились собственные отслеживаемые файлы, называется в ошибке («uncommitted changes
to TRACKED files inside submodule(s): …»), а не вменяется стору; untracked-файл внутри
submodule оставляет стор чистым.

## Какая это версия набора?

Набор версионирован. `VERSION` содержит редакцию, каждая поставляемая команда, навык
и инструмент несут метку `serpens-version:`, а `MANIFEST.sha256` фиксирует их точные
байты. Чтобы отличить файл набора от локально изменённой копии:

```bash
KV="<serpens-sdd> version"
$KV show      --root "$SERPENS_SDD_ROOT"                     # редакция набора
$KV list      --root "$SERPENS_SDD_ROOT"                     # все файлы с метками и их метка
$KV check     --root "$SERPENS_SDD_ROOT"                     # падает, если штамп расходится с VERSION
$KV verify    --root "$SERPENS_SDD_ROOT"                     # ничего не менялось с той редакции
$KV identify  --root "$SERPENS_SDD_ROOT" <файл-установки>    # pristine / MODIFIED / UNSTAMPED
```

`--root <корень-набора>` обязателен в каждом режиме: инструмент больше не живёт внутри
набора, о котором сообщает, поэтому `VERSION` и `MANIFEST.sha256` он читает оттуда, куда
указывает `--root`, а не рядом с собой. `identify` считает хеш указанного файла,
поэтому работает с установленной копией по любому пути, включая каталог команд в
домашней папке агента. `UNSTAMPED` — копия старше версионирования или ваша
собственная; `MODIFIED` — метка есть, а байты другие.

## Процесс

1. `spns-spec`: проверяет репозитории, а затем сначала определяет, где он находится: без ключа
   трекера ветки нет (спрашивает один раз и никогда не выдумывает ключ), а существующая
   ветка истории — на ней вы или нет — продолжается, а не создаётся заново. Через
   `prepare-base` идёт только ветка, которой нет нигде. Дальше создаёт изменение и запрашивает у
   CLI OpenSpec `proposal` и `specs` по одному артефакту.
2. `spns-plan`: подтверждает ветку и создаёт актуальные design и tasks.
3. `spns-implement`: подтверждает ветку, входит в OpenSpec apply и применяет Serpens TDD.
4. `spns-review`: проверяет состояние, затем выполняет `<openspec> validate <change-id> --type
   change --strict --json` и `<openspec> status --change <change-id> --json` до ревью человеком.
   Подкоманды `verify` в OpenSpec 1.10 нет.
5. `spns-test-plan` и `spns-autotest`: строят проверки из утверждённых сценариев.
   `spns-test-plan` — **black-box**: запрос или событие для отправки, ожидаемый
   ответ и ожидаемые сохранённые строки на стенде разработки — публикуется по
   `test-plan-posted-to` (из `<serpens-sdd> delivery --print-contract`), по умолчанию
   `same-ticket-comment` — комментарием в той же задаче, а не отдельной задачей на
   тестирование. `spns-autotest` — слой внутри кода.
6. Как только выполнено условие `archive-when` (из `<serpens-sdd> delivery --print-contract`) —
   по умолчанию (`after-qa-accepted`) это приёмка QA на стенде разработки, а при значении
   `after-merge` — слияние в интеграционную ветку — `spns-archive` выбирает место коммита
   архивации и запускает OpenSpec archive. Без флага он спрашивает, какое из трёх размещений
   выбрать, и никогда не решает сам;
   вариант (1) режет свежую ветку истории от подготовленной базы, имя ей даёт
   `<serpens-sdd> git-naming --print-contract <TICKET>` — без суффикса, потому что `git-naming`
   принимает только настроенную форму, и ветка с суффиксом не пройдёт pre-push guard. `--branch <имя>` задаёт её имя; `--here` архивирует в текущей ветке. Любой режим
   проходит через `assert-archivable --change <change-id>`: чистое дерево и HEAD, уже содержащий
   базу — всегда передавай `--change`: при настроенном `merge-style` проверяемый handoff-tip
   записан ПО ИЗМЕНЕНИЮ, никогда по ветке (ветка истории к моменту архивации обычно уже удалена).

Точные вызовы OpenSpec хранятся в `port-facts.md` и установленных командах.
Проверяйте их заново после обновления порта или OpenSpec.

## Обновление привязок проекта

Повторно получите привязки для сохранённого project id. Предпочитайте MCP, если
инструмент доступен; иначе обновите те же нормализованные строки вручную.
Файла `project-repositories.json` для редактирования больше нет — передайте
строки в `sync-submodules` через stdin:

```bash
export STORE_ROOT="$(git rev-parse --show-toplevel)"
printf '%s\t%s\t%s\n' service-a ssh://git@forge/project/service-a.git develop \
  | <serpens-sdd> sync-submodules --repos-from - --store-root "$STORE_ROOT"
git -C "$STORE_ROOT" submodule status
```

Хранилище, у которого с прошлой редакции ещё остался `project-repositories.json`,
может вместо этого передать `--inventory "$STORE_ROOT/project-repositories.json"`.

Новые привязки добавляются, совпадающие инициализируются, исчезнувшие показываются,
но сохраняются. Несовпадение URL, опасный путь или чужой каталог останавливают
операцию до изменений.

Для получения обновлений после проверки локального состояния:

```bash
git -C "$STORE_ROOT" submodule foreach --recursive 'git fetch --prune origin'
```

Безопасное перемещение базы делайте через `<serpens-sdd> state prepare-base` внутри
каждого репозитория. Не используйте массовый checkout или reset.

## Межрепозиторные изменения

`ticket-topology` (из `<serpens-sdd> delivery --print-contract`) в каждом поставляемом окружении
— `parent-story+child-per-repo`: используйте один родительский ticket для контракта системного
хранилища и один дочерний ticket на репозиторий (`child-created-by` решает, кто их создаёт: `ask`,
`analyst` или `agent`). Сначала создаётся контракт. Delta spec репозитория
ссылается на него по store id и spec id, но не повторяет форму. Порядок согласования:
контракт первым. Порядок реализации и merge — `merge-order` этого окружения, по умолчанию
producer, consumers, затем контракт хранилища. Изменение контракта останавливает зависимую
работу.

После обновления индексов репозиториев пересоберите каталог:

```bash
<serpens-sdd> catalog --strict "$STORE_ROOT"
```

## Восстановление состояния

| Состояние | Значение | Безопасное действие |
|---|---|---|
| detached HEAD | нет безопасной ветки истории | найдите ветку-владельца; сохраните коммиты |
| dirty при подготовке базы | правки могут быть уникальны | изучите и осознанно закоммитьте или перенесите |
| ahead от upstream | есть неопубликованные коммиты | изучите и опубликуйте либо перенесите до переключения |
| только behind | доступно безопасное обновление | выполните `prepare-base` для fast-forward |
| ahead и behind | расхождение | остановитесь; выберите merge или rebase по правилам команды |
| неверная ветка | работа может относиться к другой истории | сохраните работу и только потом переключайтесь |
| orphaned binding | списка больше нет в inventory | подтвердите владение до ручного удаления |

## Необязательный индекс Zoekt

Zoekt необязателен. Процесс работает без него. На выделенном хосте установите
`zoekt-git-index` и Universal Ctags, затем:

```bash
<serpens-sdd> index-code --store-root "$STORE_ROOT" \
  --index-dir "${SERPENS_ZOEKT_INDEX_DIR:-$STORE_ROOT/.cache/zoekt/index}"
```

Инструмент читает `.gitmodules`, проверяет все пути до индексации, требует именно
Universal Ctags и сообщает об отсутствующих подмодулях. Не ведите второй список.

## Правила работы

1. Промпты советуют, проверки и CI принуждают. Красную проверку никогда не чинят её ослаблением.
2. Лимиты отклоняют, а не подрезают. Агент перегенерирует; человек не правит сгенерированное руками.
3. Центральный каталог — подсказка маршрута. Индекс репозитория важнее каталога,
   сам репозиторий важнее своего индекса.
4. Спеки долговечны, планы одноразовы. Сомневаетесь — перегенерируйте design и tasks.
5. Каждое расхождение спеки и кода становится delta. Это рост базы спек, а не провал.
6. Та же ошибка в третий раз — остановитесь и спросите человека.

## Измеряйте внедрение

Записывайте это в заметку `baselines/` в хранилище до старта первой команды и затем
за такой же период. Оба числа берутся из чистого Git, данные CI не нужны:

```bash
# merge-коммиты за последние 90 дней — оценка частоты поставки, пока нет данных CI
git log --merges --since="90 days ago" --format=%cI | wc -l
# заархивированные изменения в репозитории — счётчик внедрения
ls openspec/changes/archive 2>/dev/null | wc -l
```

В репозиториях со squash-merge merge-коммитов нет: считайте заголовки влитых
change request (`forge-word`) через `git log --grep`.

Проверка на приписки, по каждому заархивированному изменению: proposal должен быть
старше первого коммита реализации в этой ветке.

```bash
git log --diff-filter=A --format=%ct -- "openspec/changes/<id>/proposal.md" | tail -1
```

Спека, написанная после кода, — имитация потока; считайте её как невнедрение.

Задавайте команде эти пять вопросов раз в квартал, анонимно, на уровне команды, по
шкале 1–5, плюс один свободный ответ. Формулировки не меняйте, иначе периоды
перестанут сравниваться:

1. Насколько вы довольны своим ежедневным рабочим процессом разработки?
2. Как часто вы работаете над задачей, не теряя поток на трение и ожидание?
3. Как вы оцените качество ревью, которое получаете?
4. Насколько поток SDD помогает, а насколько мешает вашей работе?
5. Порекомендуете ли вы этот поток соседней команде?

Свободный ответ: что одно нам стоит починить?

## Обновление комплекта

Существующая рабочая копия обновляется по [`docs/UPGRADE.md`](UPGRADE.md), а не
повторением установки. Прочитайте инструкцию до получения нового комплекта.

Коротко: сначала составьте опись установленных файлов через
`<serpens-sdd> version identify --root <набор>`, проверьте каждый репозиторий через
`<serpens-sdd> state prepare-base`, обновите `serpens/bin/` хранилища **и** `serpens/bin/`
каждого репозитория, переустановите команды и навыки и заново подставьте каждый
токен `<openspec>` из `port-facts.md`, останавливайтесь на каждой
копии со статусом `MODIFIED` вместо перезаписи, повторите негативные тесты и
отдельно закоммитьте каждый Git-репозиторий.

Никогда не перезаписывайте хранилище из `system-store-template/`, не запускайте
там `git init` заново и не позволяйте обновлению трогать `.gitmodules`, деревья
`openspec/` или оставшийся с прошлой редакции `project-repositories.json`.

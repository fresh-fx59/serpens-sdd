# Соглашения по веткам и коммитам

**Место:** `system-store/conventions/branching.md`. Это единственный источник правды для всего
хозяйства. Репозитории и агенты ссылаются на него, а не пересказывают его.
**Проверяется:** `tools/serpens-sdd git-naming` через lefthook (`commit-msg` + `pre-push`) в каждом
репозитории. Промпты советуют, проверки принуждают — никогда не чините красную проверку её ослаблением.

## Имя ветки

```
feature/ABCD-1234
```

- Префикс `feature/`, затем ключ тикета в трекере.
- Ключ тикета = заглавный ключ проекта, дефис, номер. `ABCD-1234`.
- После номера ничего нет. `feature/ABCD-1234-add-invoices` отклоняется — описание живёт в
  сообщении коммита и в заголовке PR, а не в имени ветки.
- Одна папка изменения = одна ветка = один тикет. Это командный поток OpenSpec
  (change = folder = branch) и то, что делает связь с трекером работающей.

**Исключения** (долгоживущие, создаются не потоком): `main`, `master`, `develop`,
`release/*`, `hotfix/*`, `support/*`.

## Сообщение коммита

```
feat(ABCD-1234): commit message text
```

- `<type>(<TICKET>): <текст>` — обратите внимание на скобки, двоеточие и один пробел после него.
- Допустимые типы: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `perf`, `build`, `ci`,
  `revert`.
- **Тикет в сообщении должен совпадать с тикетом в ветке.** Несовпадение привязывает работу не к той
  истории, и этого никто не замечает до отчёта. Проверка отклоняет такой коммит.
- Сообщения merge, revert, `fixup!` и `squash!` порождаются git, а не человеком — они пропускаются.

## Кто что делает

- **Агент** создаёт ветку и пишет сообщение коммита на шаге передачи в `spns-spec` и на протяжении
  `spns-implement`. Он обязан следовать этому файлу — поэтому шаблон продублирован в файле контекста
  агента в каждом репозитории.
- **Разработчик** никогда не переименовывает ветку так, чтобы пройти проверку, выбросив тикет. Если
  тикет неверный — неверна ветка.
- **DevOps** владеет этим файлом и подключением хуков. Изменение здесь — это изменение во всех
  репозиториях.

## Проверка того, что хуки действительно срабатывают

Хук, который установлен, но не запускается, хуже, чем отсутствие хука — всё выглядит зелёным.
**Глобальный `core.hooksPath` молча перекрывает локальные хуки любого репозитория**, включая установку
lefthook. Проверьте:

```bash
git config core.hooksPath          # ожидается пусто или каталог хуков этого репозитория
```

Если он указывает куда-то глобально — диспозер и эти проверки не работают. Почините машину, затем
докажите это намеренно плохим коммитом, который должен быть отклонён.

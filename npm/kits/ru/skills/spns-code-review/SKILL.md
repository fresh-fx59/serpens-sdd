`<openspec>` — вызов CLI OpenSpec, подставленный при установке; `<change-id>` — проверяемое изменение.

## Проведение ревью (порядок имеет значение)
0. Сначала покрытие от машины: `<openspec> validate <change-id> --type change --strict --json`
   и `<openspec> status --change <change-id> --json` сообщают невалидные артефакты (ERROR) и
   невыполненные задачи. ERROR становится блокером. Они доказывают полноту артефактов и задач,
   а не запуск теста, — доказательство прогона остаётся отдельным требованием.
1. Сначала соответствие спеке: делта-спека — это контракт. Отсутствующее поведение = блокер. ЛИШНЕЕ
   поведение, которого никто не просил, = тоже находка (расползание области скрывает баги и непроверенную поверхность).
2. Второе — честность тестов: для каждого теста спросите «упадёт ли он, если фича сломается?» Дифф, чьи
   тесты не могут упасть, — это непроверенный код с декорацией.
3. Третье — корректность: краевые случаи ИЗ СЦЕНАРИЕВ, пути ошибок, null, конкурентность.
4. Помечайте каждую находку по важности (блокер/серьёзная/мелкая) с file:line + конкретным исправлением. Никаких расплывчатых
   «стоит улучшить». Чистый дифф получает одну строку, что он чист — выдуманные находки подрывают доверие.

## Получение ревью
- Никогда не разыгрывайте согласие («отличное замечание!») — оцените находку. Если верна: исправьте, покажите
  исправленный дифф + доказательство перепрогона. Если ошибочна: скажите почему, со ссылками на код/спеку, и дайте человеку
  решить. Оба ответа уважительны; пустое согласие — нет.
- Находка, которую вы исправили, не считается закрытой, пока не переполучено доказательство (прогон тестов, verify-docs).
- Комментарии ревью о СПЕКЕ (требование кажется неверным) маршрутизируются к аналитику через трекер —
  ревью кода — не то место, где перезаключаются контракты.

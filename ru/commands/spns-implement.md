---
description: Реализовать текущее изменение по задачам с дисциплиной TDD
serpens-version: 2026-09-10.1
---
Реализуй изменение {{args}}. Следуй spns-tdd, spns-verification, spns-debugging и spns-drill-down.
`{{args}}` — это `<change-id>`; `<openspec>` — вызов CLI OpenSpec, подставленный при установке.
0. Установи `REPO_ROOT="$(git rev-parse --show-toplevel)"`. Выполни
   `<serpens-sdd> state assert-change <TICKET> --checkout --allow-dirty`.
   Он переключит на ветку истории, если ты не на ней, а она есть; создавать её он не будет.
   Остановись при неверной ветке, отсутствии upstream или расхождении. Затем выполни
   `<openspec> instructions apply --change <change-id> --json` и прочитай состояние задач:
   `state`, `progress`, `tasks`, `contextFiles`. Состояние `blocked` значит, что артефакта
   не хватает: остановись и запусти `spns-plan`. Это источник состояния, а не инструкций:
   главным остаётся цикл Serpens TDD ниже.
1. Сначала прочитай заголовок состояния tasks.md и research.md; продолжай, не выводи заново.
2. Если design.md или tasks.md отсутствуют либо устарели, пересоздай их по текущему коду.
3. На задачу: падающий тест из сценария → минимум кода → запуск → доказательство в
   tasks.md → checkbox → новое состояние. Не коммить по каждой задаче.
   Медленные тесты запускай на границе задачи.
4. При конфликте спеки и кода — включая сценарий приёмки, который больше не наблюдаем как записан —
   остановись: неполную спеку вынеси как поправку аналитику, а поправленную delta проверь
   `<openspec> validate <change-id> --type change --strict --json` до `"valid": true`;
   неожиданный код исследуй и перепланируй; нереализуемое требование эскалируй.
5. После каждой записи в openspec/ или docs/ выполни
   `<serpens-sdd> verify-docs`.
6. ЗАКОММИТЬ ВСЮ РАБОТУ ОДИН РАЗ, когда закрыты все задачи, — не по задаче. Оператор не
   выполняет git за тебя, и реализация с незакоммиченной работой не завершена. Добавляй в индекс
   ровно те файлы, которые дало это изменение, ПО ПУТИ (`git add <путь> …`). Никогда
   `git add -A`, `git add .` или `git commit -a`: в репозитории законно лежат локальные
   настройки, файлы с паролями и временный вывод, которые нельзя коммитить, а чужой
   untracked-файл — не твой. Созданный тобой файл остаётся untracked, пока ты его не добавишь.
   Коммить `feat(<TICKET>): <текст>` (или `fix(`; тип проверяет `<serpens-sdd> git-naming`),
   отправляй в `origin/feature/<TICKET>`, открывай или обновляй PR и прикладывай вывод
   `git log --oneline -1` и `git status --short`.
7. Готово только при закрытых задачах, зелёном полном наборе тестов, verify-docs и
   закоммиченной отправленной работе. Приложи свежий вывод последнего запуска.
